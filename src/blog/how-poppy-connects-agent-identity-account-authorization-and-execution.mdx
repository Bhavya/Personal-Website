An assistant handling an expense claim might retrieve a transaction through an API, open a website to attach a receipt, and contact support when the reimbursement gets stuck. From the person’s perspective, it’s still one task, but each interface may have a different way of identifying the assistant and deciding what it can do.

Poppy, or Personal Agent Protocol, connects those interactions through a common session and authorization model. It covers discovery, agent identity, OAuth grants, browser access and conversations, with an optional extension for confirming individual actions.

The engineering appeal is that a company could support delegated tasks without building a separate account relationship for every interface. I think the technical case for that approach depends on how consistently the task’s authority survives a change of interface. This review works through the mechanisms using different hypothetical workflows, including the places where the protocol leaves a consequential decision to the systems implementing it.

This review follows the working 0.3 draft as of October 25, 2026. [**Version 0.2 was published on October 24**](https://personalagentprotocol.org/docs/changelog), and some of the mechanisms discussed here are changes proposed for 0.3. The examples are abbreviated and use placeholder values.

***Discovery links a company’s domain to its authorization service***

A company publishes `/.well-known/poppy.json` to describe its supported interfaces and name its authorization issuer. The agent then retrieves the issuer’s [**OAuth authorization server metadata**](https://www.rfc-editor.org/rfc/rfc8414), which supplies endpoints and supported grants.

The discovery chain includes reciprocal checks. In 0.3, `organization.domain` has to match the host serving the discovery document, the authorization metadata’s `issuer` has to match `auth.issuer`, and its `protected_resources` list has to include the company’s origin.

Relevant fields in the company’s discovery document might be:

```json
{
  "organization": {
    "name": "Example Supplies",
    "domain": "supplies.example"
  },
  "auth": {
    "issuer": "https://auth.supplies.example"
  }
}
```

The issuer’s metadata would include:

```json
{
  "issuer": "https://auth.supplies.example",
  "protected_resources": ["https://supplies.example"],
  "scopes_supported": ["quotes:read", "orders:write"]
}
```

The [**0.3 changes**](https://personalagentprotocol.org/docs/changelog) also restrict discovery redirects to a final URL at the well-known path. Together, those checks establish a relationship between the document’s location and the issuer it names, rather than accepting either claim in isolation.

Discovery also introduces fetches of documents controlled by another party. The [**implementation guides recommend limits on redirects, response sizes and network destinations**](https://personalagentprotocol.org/docs/0.3/guides), particularly when the service retrieving metadata can reach internal infrastructure.

A procurement assistant could use this to reach an approved supplier that outsources its authorization service. Starting from the supplier’s known domain gives it a checkable route to that service. I like that the affiliation is inspectable in both directions, particularly when the login infrastructure belongs to another organization. The checks establish the claimed domain relationship, while the buyer’s policy still determines which suppliers the assistant is allowed to purchase from.

***Agent identity and session identity are separate***

A personal agent’s `client_id` is an HTTPS URL that resolves to its metadata document. The document supplies its public signing keys and callback locations. Client authentication uses `private_key_jwt`, based on [**RFC 7523**](https://www.rfc-editor.org/rfc/rfc7523).

Starting a session involves three signed objects with different purposes. The client assertion authenticates the personal agent. A separate grant assertion names the company-specific pseudonymous user, and a DPoP proof establishes possession of a fresh session key.

The grant assertion includes claims of this form:

```json
{
  "iss": "https://assistant.example/client.json",
  "sub": "opaque_user_for_this_company",
  "aud": "https://auth.shop.example"
}
```

Here, `iss` identifies the personal agent, `sub` identifies its user at this company, and `aud` identifies the company’s authorization issuer. A complete assertion also includes timestamps and a unique identifier.

The company verifies these objects before issuing a signed-out Session Token. It can recognize the agent and the pseudonymous user without that session having access to a customer account yet. Account authorization happens separately when a task requires it.

In 0.3, the session key’s thumbprint identifies the session, replacing the earlier custom `session_id` parameter. The agent’s published signing keys and its session keys therefore have separate roles: the former authenticate the agent, while the latter bind requests to a particular session.

[**DPoP, defined in RFC 9449**](https://www.rfc-editor.org/rfc/rfc9449), provides the proof-of-possession mechanism. A resource request carries a signed proof containing the HTTP method, target URI, issuance time and access-token hash, with a nonce when required.

Those fields constrain where and how a copied proof can be used, but they do not constitute approval of the complete business request. The proof does not generally cover the HTTP body, and its target URI excludes the query component. An authenticated request can consequently still contain an action or parameters outside the caller’s authority.

The guides also keep private keys and credentials outside model context. Application code can sign requests on the model’s behalf without making the model a holder of the underlying credentials.

Consider an assistant checking a shop’s return policy before accessing a customer’s order. Recognizing the agent and its pseudonymous user before account sign-in lets that interaction start without immediately requesting order access. The separation makes sense to me because identifying the software, recognizing its user and granting access to an account answer different questions. The fresh session key also gives the session its own cryptographic identity, but it doesn’t by itself restrict which returns the assistant can initiate.

***Account authorization builds on OAuth grants***

Direct Sign-In uses the authorization code flow with [**PKCE**](https://www.rfc-editor.org/rfc/rfc7636). Device Sign-In uses the [**device authorization grant**](https://www.rfc-editor.org/rfc/rfc8628), allowing the person to authorize through another device. The working draft prefers those flows over Mediated Sign-In, where the agent submits the person’s credentials.

Poppy calls the resulting access token a Session Token and the refresh token an Account Token. Their underlying [**OAuth roles**](https://www.rfc-editor.org/rfc/rfc6749) remain familiar: an access token is presented to a protected resource, while a refresh token obtains subsequent access tokens.

The company defines its own scopes in 0.3, rather than prescribing one universal set of agent permissions. The protocol requires those scopes to be enforced across the supported interfaces, including actions performed through the company’s conversational agent.

This means scope enforcement extends beyond the API gateway. If a support tool executes with broader service credentials, the connection between the caller’s grant and the tool’s authority still has to be preserved. Passing the scopes into a prompt supplies context but does not enforce them at execution time.

The company also keeps session and grant records, including the account association and granted scopes. An Account Token can obtain access for new sessions, so ending a session is different from revoking the agent’s access to the account.

[**Token revocation**](https://www.rfc-editor.org/rfc/rfc7009) affects the relationship between that stored state and already-issued access tokens. A self-contained token can remain cryptographically valid after its grant is revoked. Whether it remains usable depends on invalidation, a current-state check or the remaining token lifetime.

The [**draft’s account of what it adds to OAuth**](https://personalagentprotocol.org/docs/0.3/spec#what-poppy-adds-to-oauth) also identifies custom work for the self-issued session grant. Existing OAuth infrastructure supplies useful components, but supporting Poppy still involves implementing its session semantics.

For a calendar assistant, a hypothetical `calendar:read` grant could cover checking availability, while `calendar:write` could cover creating or changing events. That’s a useful boundary, but a write grant may still permit both moving a private reminder and sending an invitation to two hundred people. My concern is how easily a broad account permission can be mistaken for permission to complete a particular task. Poppy carries the grant across interfaces, while the application still needs a way to represent the narrower instruction and decide when additional approval is necessary.

***The same session can be used through different interfaces***

Poppy can advertise OpenAPI APIs and remote MCP servers. The working draft uses DPoP where supported, with [**OAuth Token Exchange**](https://www.rfc-editor.org/rfc/rfc8693) providing a compatibility path to a Bearer token for an MCP server that does not support DPoP.

The exchanged token is restricted to its target MCP resource. That limits where it can be used, although possession of the Bearer token is still sufficient to use it within its authority and lifetime. The fallback therefore has a different security property from the proof-of-possession path.

Browser access has its own mechanism. In 0.3, the company issues a one-time code tied to a browser cookie. The agent signs a proof using its session key, and verification allows the company to set the corresponding session cookie. The guides recommend isolated browser storage for each session.

The website then evaluates requests under that session’s scopes. This lets browser activity share authorization context with API activity, although the transports and their credentials remain different.

Using the person’s already-authenticated browser is still an [**open design discussion**](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/32). A person and an agent sharing the same cookies creates an attribution problem: signed requests can identify cooperative agent activity, but an unsigned request is not necessarily evidence of human activity.

For an expense assistant, the API might expose transaction data while receipt attachment is available only through the website. Sharing authorization context avoids a second, unrelated login for that step. I think this is one of Poppy’s more practical design choices, provided the website actually enforces the assistant’s grant. Giving the assistant the employee’s fully authenticated browser could instead expose reimbursement settings or payment details outside that grant, which makes browser isolation part of the authorization argument, not just a convenience for managing cookies.

***Conversations preserve context through retries and handoffs***

Conversations add another kind of persistent state. The official [**conversation implementation pattern**](https://github.com/personal-agent-protocol/personal-agent-protocol/blob/main/skills/implement-personal-agent-protocol/patterns/conversations.md) describes an adapter with an ordered event log, cursors and message-ID deduplication in front of an existing support platform.

`status` records whether work is ongoing, idle, queued or closed, while `responder` identifies whether a human or agent is handling the company side. Message deduplication allows a retried initial request to recover the existing conversation instead of creating a second one.

A handoff changes who responds without inherently granting more authority. The conversation’s account context and the permissions applied to its tools remain relevant even when the next step is handled by a different model or a person.

Imagine an assistant disputing a broadband bill. The company’s agent may need to refer the case to a person, and a dropped connection shouldn’t create a second dispute or lose the first response. Stable conversation and message identifiers help preserve that continuity. I think the separation of responder from status is useful here: a case being assigned to a human tells the assistant something about who is handling it, but it says nothing by itself about whether a credit has been issued. The conversation can carry the negotiation, while a consequential adjustment still needs an explicit outcome.

***Operations ties confirmation to a particular set of terms***

The optional [**Operations extension**](https://personalagentprotocol.org/docs/0.3/extensions/operations) represents an action as a shared record with versioned terms. The company proposes an operation and the agent confirms a particular revision after obtaining approval or applying a standing permission that covers it.

An abbreviated booking proposal might look like this:

```json
{
  "operation_id": "booking_42",
  "revision": 2,
  "state": "proposed",
  "summary": "Book one room for October 30–31 for USD 240, non-refundable.",
  "terms": {
    "arrival": "2026-10-30",
    "departure": "2026-10-31",
    "total": { "amount": "240.00", "currency": "USD" },
    "refundable": false
  },
  "expires_at": "2026-10-26T12:00:00Z",
  "confirmation": null,
  "result": null
}
```

The corresponding confirmation names the revision:

```json
{
  "revision": 2,
  "approved_by": "user"
}
```

Before execution, the company checks the operation’s revision, scopes, expiry and approval mode. A repeated confirmation is required to return the existing state rather than perform the action again.

The extension also distinguishes a failed action from an unknown outcome. If a downstream call times out and the company cannot establish whether it took effect, the operation stays in progress.

That requirement has consequences for the execution adapter. Recording a confirmation and dispatching work to another system are separate steps that can fail independently. Depending on the dependency, preserving the operation’s semantics can involve durable dispatch, downstream idempotency or reconciliation.

The record also has a specific evidentiary limit. It establishes that the personal agent asserted approval of a revision, but it does not independently establish that the person saw or approved those terms. The extension explicitly acknowledges that trust boundary.

In the hotel example, a price change while the person is considering the proposal needs a new revision, and a timeout after confirmation needs recovery of the existing operation. Booking another room would be a poor response to uncertainty about the first one. I think this is the strongest part of the design because it gives approval and recovery a shared business record, beyond the lifetime of one HTTP request. Its value still depends on the execution system preserving those semantics, and the approval assertion leaves the company relying on the agent’s account of what the person authorized.

***Where this leaves the integration***

Across these examples, Poppy gives the company and the personal agent a common way to refer to the actor, the account grant, the ongoing interaction and, when the extension is used, the proposed action. That could remove a considerable amount of bespoke coordination between interfaces, although it still leaves meaningful engineering work behind each one.

The part I keep coming back to is whether a restriction survives every available route to an action. If an API rejects a change but a browser session or support tool can complete it under broader credentials, the signatures can all be correct while the delegation is still too broad. That’s an integration problem the protocol helps describe, even where it doesn’t supply the enforcement.

The [**path to 1.0**](https://personalagentprotocol.org/docs/path-to-1) includes further work around payments, push notifications, attachments and self-hosted agents. As those capabilities develop, I think the most revealing cases will be ordinary tasks that encounter an exception: the missing receipt, the disputed bill or the booking whose result is uncertain. Those are the points where an assistant needs to keep working, but carrying the task forward shouldn’t quietly expand what it has permission to do.
